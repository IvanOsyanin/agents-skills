# Извлечение модели из кода

Работай с текущим рабочим деревом. Документация помогает найти код, но не доказывает
подключённость маршрута, существование интеграции или фактический порядок операций.

Собери небольшой реестр рядом с результатом:

| ID | Тип | Название | Исполнитель/владелец | Основание | Статус |
| --- | --- | --- | --- | --- | --- |
| F1 | функция | Принять документ | API | путь, символ/строки | реализовано |
| D1 | данные | Копия документа | объектное хранилище | адаптер записи | реализовано |
| E1 | обмен | Содержимое файла | API → хранилище | вызов в сервисе | реализовано |
| F2 | функция | Проверить версию формы | внешняя система | пункт интеграционного плана | целевое |

Дополняй реестр только существенными для задачи полями:

- Компонент: ID, родительская система/компоненты, полное имя `АС. Компонент`,
  модульная ответственность, внутренний/внешний контур,
  подтверждённый стек/размещение, основание. Контракт и конкретный продукт разделяй.
- Функция: ID компонента + ID функции, одно каноническое имя для обоих представлений,
  вход, наблюдаемый результат, опубликованный сервис или внутренняя функция;
  соответствующие шаги/подшаги и листы. Имя функции не является уникальным ключом.
- Данные: ID, смысл/состав, логический владелец, физическое место при его наличии,
  срок жизни (постоянно, временно, в памяти, транзит), создатель/потребитель.
- Обмен: ID и сквозной номер интерфейса (разные поля), поставщик сервиса/мастер-система,
  инициатор вызова, компонент и функция источника основных данных, получатель,
  данные запроса/события, данные ответа (если есть), синхронный/асинхронный режим,
  условие и протокол, если подтверждены. Ответу укажи обратное направление.
  Сохрани категорию ИБ и статус изменения только при явном основании. Технические
  ответы и транспорт не обязательно отображать на информационном листе.
- Сценарий: ID/название, инициатор, вход, шаги, условия, результаты и ссылки на
  функции; основание/источник сценария и отметка о покрытии в итоговой
  информационной и функциональной схемах.

«Неизвестно» и «не входит в область» — допустимые значения с пояснением.
Не превращай этот перечень в обязательные пустые таблицы и не заполняй пробелы
догадками. Основания и статус указывай также для спорных деталей, а не только
для компонента целиком. Для целевых требований ссылайся на пункт плана;
не присваивай плану статус реализации из-за похожего имени класса.

Символ функции устойчивее номера строки; по возможности сохраняй оба. Не придумывай
«доказательства» по одному имени файла. Для существенного отсутствия функции проверь
точки сборки и подключённые маршруты/задачи.

Проверяй, когда это относится к сценарию:

- Кто инициирует работу: пользователь, HTTP, сообщение, таймер.
- Что реально приходит на вход: байты, multipart, URL, ID, поля формы.
- Кто вызывает внешнюю систему и кто проверяет её результат. Проверка хеша
  приложением не становится бизнес-функцией объектного хранилища.
- Какие данные сохраняются, какие живут в памяти, какие передаются транзитом.
- Где заканчивается транзакция; как соотносятся фиксация, публикация и подтверждение.
- Что запускается независимо от ответа клиенту; где повтор, ошибка и окончательный итог.
- Как клиент получает и применяет результат; может ли устаревший ответ изменить состояние.
- Какие зависимости необязательны; является ли сторонний сервис установленным продуктом
  или только OpenAI-совместимым контрактом/планируемым размещением.

Уровень раскрытия выбирай по задаче. Схема бизнес-сценария не обязана раскрывать
heartbeat и connection pool. Но она не должна превращать повтор в успешное
завершение или последовательные независимые операции — в общую транзакцию.

Сверь две проекции по ID **и точным именам**. Реестр сценариев используй как
чек-лист полноты: каждый сценарий в согласованной области должен быть отражён в
обеих проекциях там, где это уместно. Несколько атомарных функциональных
шагов могут детализировать одну прикладную функцию; сохрани родительские имя/ID.
Каждая сущность имеет отдельный ID; её цилиндр и передаваемый экземпляр могут
иметь общий ID с разными ролями. Проверь сквозной номер и поставщика интерфейса
независимо от направления его данных. Транзит не превращай в владение сущностью.
Общий контейнер не должен скрывать ошибочную зависимость отдельного процесса.
Сохрани реестр свойствами фигур Draw.io либо отдельным согласованным файлом.
При запросе «оставить только схемы» предпочти свойства фигур; не создавай рядом
обязательную документацию, которую пользователь не запрашивал.
